How to use this dashboard

Weekly Google Search Console data for every Nilotpal-authored Vantage Circle blog post, going back 52 weeks. Auto-refreshes every Monday at 10 AM IST; manual refresh via ./refresh.sh.

The two lenses

Every post is measured two ways. The disagreement between them is the most useful signal.

URL-level (all queries)

Impression-weighted avg position across every query GSC saw the page surface for. Answers: "how is this URL doing overall?"

Target keyword

Position for one specific query — the one the post was written to win. Defined per slug in target_keywords.json. Answers: "is this page ranking for what I wrote it for?"

Example: A page can show URL-level pos 13.5 (page 2) but target pos 16.1 — meaning it's getting traffic from a different query than its slug suggests.

Top controls

  • Window selector (4 / 12 / 26 / 52 weeks or Custom) — sets the "current" period. All Δ comparisons are vs the equally-sized window immediately before it.
  • Summary CSV / Weekly CSV — exports the current view (Summary) or all 52 weeks of history per slug (Weekly).

Reading a row in the Rank Tracker

  • Title + slug
  • ↳ Target keyword with a badge:
    • target — you defined it manually in target_keywords.json. Trust this row.
    • top query — auto-fallback to the highest-impression query (no manual entry). May or may not be the true SEO target.
  • POS — avg position for the target keyword in the current window. "—" means no impressions for that exact query.
  • Δ — change vs prior window. ▲ green = rank improved (number got smaller); ▼ red = rank worsened.
  • Bucket — Page 1 (≤10) / Page 2 (10.01–20) / Page 3+ (>20) / No data.
  • Trend — sparkline of POS over the current window. First → last position printed below.

Inside the post-detail modal

Click any row to open the modal. Layout:

  • Two stat rows side by side: URL-level (top) and Target keyword (bottom). Both show Position / Δ / Impressions / Clicks·CTR for the current window.
  • Trend chart — weekly time series with shaded current/prior windows. Two toggles:
    • URL / Target — which data source to chart
    • Position / Impressions / Clicks / CTR — which metric to show
  • Top Queries — every query the page ranks for in the window, sorted by impressions. This is where you spot queries the page is winning for that aren't your target.
  • Weekly history table — all 52 weeks, respects the URL/Target toggle.

What to look for (workflows)

Weekly check-in · 5 min
  1. Overview tab → read the delta cards. Any metric down >10%?
  2. Movers tab → "Fell off Page 1" section first. Each post here is a real loss.
  3. Rank Tracker → click the Δ column header twice to sort by biggest drop. Top of list is what to investigate.
Monthly optimization run · 30 min
  1. Striking Distance → sort by impressions, pick top 3, queue for content/SERP-feature improvements.
  2. CTR Fixes → top 3, rewrite titles and meta descriptions (not full content).
  3. Queries tab → "Striking distance only" checkbox → find query-level wins on pages you already own.
Audit target keywords · 10 min
  1. Rank Tracker, look for grey top query badges — those are the dashboard's guesses. Confirm or override.
  2. For green target rows showing "No data": click in, scan Top Queries — is the page ranking for something else? If yes, your target may be wrong.
  3. Edit target_keywords.json, run ./refresh.sh.

Reading patterns

  • URL-level POS ≪ target POS → page ranks for non-target queries. Consider changing the target.
  • "No data" target + active URL traffic → page is alive but not ranking for the intended keyword. Content/intent mismatch, or wrong target.
  • Gradual decline on trend chart → SEO/content erosion. Refresh, update internal links, add depth.
  • Sudden drop on a specific week → algorithm update, technical issue (broken redirect, deindexing), or a competitor moved in. Check the SERP and search algo update calendars for that week.
  • High impressions + low CTR + page 1 → title/meta problem, or competing for the wrong intent (e.g. ranking for a navigational query you can't satisfy).
  • Striking-distance + climbing trend → already moving up; small push could land it on page 1.

Glossary

  • Position — GSC's avg position. The rank the page held when it appeared in a SERP, averaged across the window weighted by impressions. Not the same as a single live SERP check — GSC averages across geos, devices, query variants, personalization.
  • Impressions — number of times the page appeared on a SERP (any depth).
  • Clicks — clicks from SERP to the page.
  • CTR — clicks ÷ impressions.
  • Δ vs prior — current window minus prior window. Inverted for display: lower position number = better rank, so a negative Δ is shown as a green ▲.
  • Bucket — Page 1 (avg pos ≤ 10), Page 2 (10.01–20), Page 3+ (>20), No data (zero impressions in window).

Limitations

  • Avg position ≠ live rank. Manual SERP checks will often disagree with GSC, especially for pages with few impressions.
  • 52-week ceiling. History older than 52 weeks isn't stored.
  • Exact-string keyword match. "becoming employer of choice" won't match "how to become an employer of choice". A page can show "No data" for its target while still ranking for variants — check the Top Queries inside the modal.
  • Drafts excluded. Slugs ending in -draft are skipped.
  • One author. Filtered to Astro frontmatter author containing "nilotpal".
  • 2-day GSC lag. The most recent ~2 days of data are not yet finalized and aren't pulled.
  • The newest week is provisional. Because of that lag the latest week is always short — measured against snapshots a week apart it comes in about 16% low, then revises up. Weeks older than that don't move. It's drawn with a dashed segment and a hollow marker, tagged provisional in the weekly table, and flagged in the period line. Don't read the final point as a trend.
  • Zero vs. no data. An empty window renders as zero either way. When the underlying file has no rows for the selected weeks, a banner appears at the top of the page saying so — a data gap, not a traffic drop. Views on the Queries tab read queries.js; every other tab reads rankings.js, and the two can drift if a refresh is only partly committed.
  • Avg Position is impression-weighted. If a post loses its high-volume page-1 terms and only long-tail page-4 impressions remain, the average worsens even though nothing was demoted. The Overview tile shows the median across posts underneath as a cross-check, and the Rank Tracker tab avoids the problem entirely by using target-keyword rank.

Reading the visuals

  • Colour means one thing throughout. Rank buckets are an ordered good-to-bad scale, so they use a diverging pair: page 1 blue, page 2 neutral grey, page 3+ red. Page 1 is blue in the chips, in the distribution bar and in the mover bars — never a different colour in a different place.
  • Why not green/amber/red? It fails the contrast check on amber, and puts the two ends of the scale on the red/green axis that colour-blind readers can't separate. The blue↔red pair is distinguishable under every simulated form of colour vision. Every colour is also labelled in words, so nothing depends on seeing hue.
  • "Where the portfolio ranks" is centred on page 2: page 1 grows left, page 3+ grows right. A healthy portfolio leans left. Both windows share one scale, so the two bars are directly comparable.
  • "The long view" is the only absolute chart — every tracked week, not a comparison. The selected window is shaded blue, the prior window grey. Hover any week for its numbers, or hit Table for all of them at once.
  • Bar length is always literal. Impression bars in the table are linearly proportional, so a post with a tenth the traffic gets a tenth the bar. Most rows show almost nothing because their volume genuinely is almost nothing.
  • Green and red arrows mean direction of change, which is a different job from rank bucket. ▲ green = improved, ▼ red = declined, and the arrow is always there so colour never carries it alone.

When the dashboard warns you

  • Amber "data is N days old" — the Monday refresh hasn't run in over 10 days. Run ./refresh.sh and check ~/.blog-rank-tracker.log. Turns red past 21 days.
  • Amber "missing N of M weeks" — the active tab's data file is partly stale. Totals and Δ are understated; don't act on them.
  • Red "no data for this window" — the file has nothing for these weeks at all. Every number below is meaningless until refreshed.

Files in the repo

  • target_keywords.json — slug → primary keyword mapping. Edit this to fix wrong targets, then re-run refresh.
  • rankings.js — auto-generated per-post data (URL-level + target-level history).
  • queries.js — auto-generated per-query data (top ~25 per post).
  • update-data.py — refresh script. Pulls GSC, regenerates the JS files.
  • refresh.sh — runs update-data.py, commits, pushes. Use this to apply changes to the live dashboard.
